# How We Build

I began with the source rather than designing an imagined lead list. The URL resolves to an 11.06 GiB compressed service-observation snapshot, not a customer master. I read a capped prefix, checked its actual fields, and designed the first workflow around what those observations can support: safe grouping, time-bounded technical clues, an analyst queue, and an ownership check before any sales conversation. Salesforce's own public prospecting guidance is a useful sanity check: qualification is ongoing, sellers need to reach the right person, and a scoring system is only as useful as its underlying data.

I used the Copilot coding-agent workflow to build a standard-library Python importer, rules engine, service endpoints and evaluator, then parallelized a separate frontend implementation and documentation/evaluation package. I exercised the source import, refreshed ranking logic against the resulting observations, and added test coverage for stale/future dates, hosting ambiguity, duplicate observations, weak and strong signals, trace recording, token-cost math, API error handling, and CSV export. Versioned prompts, a reusable SKILL, synthetic edge-case evaluation set and local trace store make the optional model workflow inspectable, not a hidden prompt call.

AI saved the most time turning a broad brief into parallel application surfaces and drafting test cases, schemas and handoff documentation. It also made it easier to explore an optional model integration while keeping the deterministic score, validation and cost guardrails in ordinary code. It cost more than direct coding when inference-driven assumptions outpaced investigation—for example, the input looked at first like ordinary firmographics, but inspection showed it was raw infrastructure data. I repeatedly corrected false certainty by distinguishing a domain candidate from company ownership, a port from authentication state, and an observation from buying intent.

The known weakness I would tell a teammate first: this prefix has no company identity, firmographics, valid ICP, contacts, buying activity or sales outcomes. The domain/provider heuristic and synthetic labels need review and real, authorized ground truth before any sales team treats the ordering as predictive. Public hosting has been prepared but not executed; this remains a shared-workspace prototype, not multiuser production software.

**Hosting follow-up:** after the owner chose free PythonAnywhere hosting and requested Flask, I replaced the prior hosting configuration with Flask routing over a shared WSGI transport, private reviewer credentials, a healthcheck and persistent account-home SQLite. The adapter reuses the existing API rather than maintaining separate hosted/local business logic. I also prepared a frozen blind real-data review packet and label importer; the owner must still provide human judgments and run live-model measurements before claiming requirement completion.

**AI-generated data disclosure:** the 24 synthetic evaluation examples are AI-authored illustrative policy cases, not independently hand-labeled customers. The additional real-data review sheet is blank, not a substitute for human review. The checked-in baseline is a measured run of local deterministic policy, not an LLM benchmark. No live model calls, public website or Loom recording are claimed.
